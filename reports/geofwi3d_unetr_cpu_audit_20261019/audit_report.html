UNETR: CPU audit of the GeoFWI3D seed search

19 October 2026 · Audit completed 11:42 Rome time · No GPU jobs, optimizer updates, or campaign changes

The current UNETR recipe has a large generalization gap. The evidence does not establish that the FLOPs cap is too small. All 25 completed UNETR seeds fail on fold 0, and all peak before the budget is exhausted. More seed searching is unlikely to be a good use of the current compute allowance.

The average validation curve peaks at 33.55% near update 207 and ends at 29.96%, while mean training loss falls from 0.436 at update 207 to 0.399 at update 414. This is consistent with overfitting or learning features that do not transfer. It is not a controlled causal comparison of budgets or recipes.

The latest saved campaign state is paused, with 77 completed runs: 26 nnU-Net, 26 SwinUNETR, and 25 UNETR. UNETR seed 25 was interrupted and retained for recovery. No 3D U-Net or folds 1–2 have completed in this search, because fold-0 UNETR rejects each seed.

What is wrong with the predictions?

At the final checkpoint, UNETR both misses salt and labels background as salt. Across 25 seeds, mean validation precision is 30.95% and recall is 36.61%: about 69.05% of predicted salt is wrong, and 63.39% of true salt is missed. These are voxel-pooled ratios computed per seed, then averaged; the headline Dice is mean per volume.

On the training set, recall is 98.68%. The model is therefore not simply predicting background everywhere or failing to receive useful gradients. Predicted validation salt volume is 1.32 times the true salt volume on average, but much of it is in the wrong voxels. Threshold tuning is not established as a remedy; saved confusion counts alone cannot reconstruct a threshold-response curve.

On matched seeds 0, 14, and 18, nnU-Net beats UNETR on every one of the 96 validation volumes. SwinUNETR beats it on 96, 96, and 88 volumes, respectively. The problem is broad, not a few outlier masks dragging down the mean. Across all 26 completed baseline seeds, nnU-Net and SwinUNETR both exceed 50% on fold 0.

An additional CPU-only check used a fixed spatial mask learned from the 19 training labels, with its threshold selected by leave-one-training-volume-out Dice. It achieves only 16.48% validation Dice. UNETR does better than this simple spatial prior; this does not reveal what features it actually learned.

What was checked, and what was ruled out?

  • Data integrity: all 319 packaged images and masks; 638 SHA256 checks passed. Every pair has native 96³ shape, matching affines, finite normalized image values in [-1,1], binary nonempty masks, and salt voxel counts matching the provenance manifest. No duplicate image/mask hashes were found.
  • Splits: 19 training and 96 validation volumes per fold, no case or simulation-seed overlap within a fold, and disjoint validation sets across all three folds. Archived run configurations match the intended splits exactly.
  • Preprocessing: the same image-only percentile normalization and loader are used for training and validation and for all four models. Fold-0 image standard deviation is similar (0.208 training versus 0.210 validation), and clipping is 0.5% in both sets. Mean salt fraction differs (6.38% training versus 8.96% validation); this is a descriptive small-sample difference, not proof of distribution shift or its cause.
  • Metrics: recomputed Dice from all confusion matrices in final validation, best validation, and final training files for 31 runs: all 25 UNETR runs plus six matched baseline runs. This covers 6,541 case/checkpoint records. Ground-truth voxel totals match local masks exactly. No background-Dice averaging, class reversal, missing cases, or arithmetic discrepancy was found. Voxel-pooled UNETR Dice is also low (31.50%), so per-volume averaging is not the explanation.
  • Archive/source consistency: 189 downloaded result/configuration files match their archive hashes; 124 recorded training/loss source hashes match the frozen bundle. All audited runs record torch 2.12.1 and MONAI 1.6.0, no augmentation, no smoke mode, and zero discarded optimizer attempts.
  • Model identity: the builder selects MONAI UNETR, with one input channel, two output channels, feature size 16, hidden size 768, 12 attention heads, and 92,802,274 parameters. The log label “unet” is a shared trainer alias; it does not mean a plain U-Net was accidentally trained. The exact recorded MONAI 1.6.0 package reproduces the parameter count on CPU.
  • Loss: the agreed background-inclusive Dice-only objective is actually used; no auxiliary constraint term is active. CPU loss values and gradients match an independent softmax/one-hot Dice calculation. Perfect and inverted synthetic masks produce losses 0 and 1. This rules out the tested loss-wiring errors, not all possible CUDA numerical effects.
  • Optimization: AdamW at initial LR 1e-4, weight decay 1e-5, 24 warmup updates, and the frozen 477-update cosine horizon. All 500 logged LR values across UNETR seeds match recomputation. Every completed run uses 414 updates (21.79 passes over 19 volumes), consuming 99.866% of its allowed optimization FLOPs. The remainder cannot fund one more update.
  • Train/eval behavior: the model returns to training mode before each update; evaluation uses eval mode. This UNETR has no BatchNorm, zero dropout, and InstanceNorm without running statistics, so the usual stale BatchNorm/dropout mode explanation is not supported. Best checkpoint tensors are cloned, avoiding reference mutation.

Interpretation and the next compute decision

Supported: the present recipe fits the small training set much better than unseen volumes. Failure is stable across seeds; later updates usually lower validation Dice. Not established: which specific change will solve it, whether any seed under this recipe can exceed 50%, or whether a carefully rescheduled larger-budget run would improve performance.

The combination of a 92.8-million-parameter model, 19 training volumes, no augmentation, training from scratch, and Dice-only optimization is a plausible contributor. The audit cannot isolate capacity, data diversity, loss choice, regularization, and learning rate without new controlled runs. The agreed Dice-only recipe is implemented correctly; it is an experimental choice, not an implementation bug.

As a reference, the MONAI UNETR BTCV implementation uses Dice+CE (with squared Dice), while this campaign intentionally uses Dice-only. That makes adding CE a reasonable hypothesis to test, not a guaranteed fix or proof that the current implementation is invalid. Official UNETR reference implementation.

  1. Now: leave the campaign paused. Do not spend more on random seeds or raise the budget solely on the assumption that 414 updates are insufficient.
  2. First future GPU comparison: one predeclared fold-0 seed, such as seed 0, changing only the loss to current Dice plus CE. Keep the data, augmentation policy, architecture, optimizer and frozen LR trajectory unchanged. Re-profile the changed loss and choose the update count from the same 182,178.13 GFLOP cap; compare with the archived seed-0 control. This is a new recipe/version, and success is not guaranteed.
  3. Budget comparison, only if justified later: define the extended LR schedule explicitly. The existing cosine function is not clamped after its 477-update horizon; simply extending updates past that horizon would eventually raise the LR again. No current 414-update run reaches that region.
  4. Once a recipe is viable: screen UNETR first on all three folds, then verify the same candidate seed on the other models. Keep replacing failures until three seeds pass all 12 model/fold conditions. Retain rejected results and identify the cohort as validation-selected.

A completed UNETR run took about 14.7 minutes inside the recorded trainer on the existing GPU setup (median; this excludes some setup and archive overhead and is not a future-runtime guarantee). No such run was started by this audit.

Limits and reproducibility

Completed checkpoints and prediction volumes were retired under the storage policy. The audit therefore cannot re-run those models, inspect spatial error maps, change inference thresholds, or compare FP32 with BF16 predictions. Raw physical vp/rgt archives are not included in the packaged data; label derivation was checked against provenance and mask counts rather than regenerated from those raw archives. All model results here are fold 0.

CPU contracts used MONAI 1.6.0 and local torch 2.2.2; CUDA runs used torch 2.12.1. A preliminary local MONAI 1.4.0 parameter check was version-mismatched and discarded; checks were repeated with the exact MONAI 1.6.0 wheel in an isolated temporary directory. The project environment was not changed. The archived GPU preflight remains the evidence for the original CUDA checkpoint replay.
